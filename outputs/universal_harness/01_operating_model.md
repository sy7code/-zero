# 01. Operating Model

## 1. 기본 원칙

모든 프로젝트는 다음 원칙으로 운영한다.

- 계약 없는 병렬 개발을 시작하지 않는다.
- 기능 구현과 검증을 분리하지 않는다.
- 보안은 마지막 점검이 아니라 설계 단계부터 포함한다.
- 실패 경로를 정상 경로만큼 명시적으로 다룬다.
- 외부 연동은 타임아웃, 재시도, fallback, 로그를 포함해서 설계한다.
- 코드는 한 번에 크게 합치지 않고 작은 단위로 검증하며 합친다.

## 2. 표준 개발 흐름

```text
Discovery
  -> Foundation
  -> Vertical Slice
  -> Expansion
  -> Hardening
  -> Release
  -> Post-release Review
```

### Discovery

목적:

- 목표, 사용자, 범위, 위험을 명확히 한다.

필수 산출물:

- 문제 정의
- MVP 범위
- 범위 밖 항목
- 핵심 사용자 흐름
- 주요 위험 목록

### Foundation

목적:

- 병렬 개발 전에 공통 계약과 골격을 만든다.

필수 산출물:

- 프로젝트 구조
- API 계약 초안
- 데이터 모델 초안
- 환경변수 목록
- 로컬 실행 방법
- 공통 응답 형식
- 기본 CI 또는 로컬 검증 스크립트

### Vertical Slice

목적:

- 가장 작은 사용자 흐름을 처음부터 끝까지 연결한다.

필수 산출물:

- 최소 화면 또는 엔드포인트
- 최소 DB 저장
- 최소 응답 표시
- 실패 시 fallback

### Expansion

목적:

- 기능을 넓힌다.

필수 산출물:

- 세부 기능
- 예외 처리
- 외부 연동
- 권한 처리
- 테스트 케이스 확장

### Hardening

목적:

- 보안, 안정성, 유지보수성을 강화한다.

필수 산출물:

- 입력 검증
- 인증/인가 검증
- 파일/외부 입력 검증
- 에러 응답 정리
- 로그 정리
- 회귀 테스트
- 문서 최신화

### Release

목적:

- 배포 또는 발표 가능한 상태로 고정한다.

필수 산출물:

- 릴리스 체크리스트
- 데모 또는 운영 시나리오
- rollback 또는 fallback 계획
- known issues

### Post-release Review

목적:

- 릴리스 후 실제 동작과 개선점을 확인한다.

필수 산출물:

- 오류 기록
- 사용자 피드백
- 후속 개선 목록
- 재발 방지 항목

## 3. Definition of Ready

기능 구현을 시작하려면 다음 조건을 만족해야 한다.

- 목적이 한 문장으로 설명된다.
- 입력과 출력이 정해져 있다.
- UI 또는 API 계약이 있다.
- 데이터 저장 여부가 정해져 있다.
- 실패 경로가 최소 1개 이상 적혀 있다.
- 보안이나 개인정보 영향이 확인되어 있다.
- 테스트 방법이 적혀 있다.

## 4. Definition of Done

기능은 다음 조건을 만족해야 완료다.

- 요구사항에 맞게 동작한다.
- 정상 경로와 실패 경로가 검증되었다.
- 입력값 검증이 있다.
- 에러 메시지가 사용자에게 안전하다.
- 로그에 민감정보가 없다.
- 관련 문서가 갱신되었다.
- 리뷰를 통과했다.
- 기존 핵심 흐름을 깨지 않는다.
