# 09. Testing Strategy

이 문서는 프로젝트 검증 전략을 정의한다. 테스트는 단위 테스트만 뜻하지 않는다. 자동 테스트, 수동 검증, 보안 검증, 회귀 검증을 모두 포함한다.

## 1. 테스트 피라미드

기본 구조:

```text
많이 작성: unit test
중간 작성: integration test
적게 작성: end-to-end test
항상 수행: smoke test
```

## 2. Unit Test

대상:

- 순수 함수
- 비즈니스 규칙
- 입력값 검증
- 체크리스트 매칭
- 권한 판단
- 데이터 변환

원칙:

- 외부 API와 DB에 의존하지 않는다.
- 빠르게 실행되어야 한다.
- 실패 원인이 명확해야 한다.

## 3. Integration Test

대상:

- API와 DB 연결
- 파일 업로드
- 인증/인가
- 외부 API client
- 메시지 큐 또는 비동기 작업

원칙:

- 실제 DB 또는 테스트 DB를 명확히 구분한다.
- 외부 API는 mock과 실제 호출을 분리한다.
- 실패 경로를 반드시 포함한다.

## 4. End-to-End Test

대상:

- 사용자가 실제로 수행하는 핵심 흐름
- 결제, 가입, 업로드, 결과 조회처럼 여러 계층을 지나는 흐름

원칙:

- 수를 많이 늘리지 않는다.
- 릴리스 전 핵심 시나리오 검증에 사용한다.
- 데이터 초기화 방법을 명확히 둔다.

## 5. Smoke Test

릴리스 또는 발표 직전 반드시 확인한다.

- 앱 또는 웹이 실행되는가
- 백엔드 health check가 성공하는가
- DB 연결이 되는가
- 핵심 API 하나가 성공하는가
- 로그인 또는 기본 인증 흐름이 되는가
- 핵심 사용자 시나리오가 한 번 성공하는가

## 6. Regression Test

버그를 수정할 때는 같은 문제가 다시 생기지 않게 한다.

규칙:

- 버그 재현 조건을 기록한다.
- 가능하면 자동 테스트를 추가한다.
- 자동화가 어렵다면 수동 체크리스트에 추가한다.

## 7. Security Test

필수 항목:

- 인증 없이 보호 API 호출
- 다른 사용자 리소스 접근
- 잘못된 파일 업로드
- 비정상 enum 값
- 과도하게 긴 문자열
- secret 노출 여부
- 에러 응답 내부 정보 노출 여부

## 8. Test Evidence

PR 또는 merge 전에 최소한 다음 중 하나를 남긴다.

- 테스트 명령과 결과
- Swagger/Postman 검증 결과
- 수동 시나리오 체크 결과
- 실패했지만 허용한 known issue
