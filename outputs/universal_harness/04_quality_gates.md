# 04. Quality Gates

## 1. Gate 0: Design Gate

통과 조건:

- 목표와 범위가 명확하다.
- 범위 밖 항목이 있다.
- 사용자 흐름 또는 시스템 흐름이 있다.
- 주요 위험이 적혀 있다.
- 테스트 방법이 정해져 있다.

실패 시 조치:

- 구현을 시작하지 않는다.
- 범위를 줄이거나 계약을 보완한다.

## 2. Gate 1: Contract Gate

통과 조건:

- API request/response가 정의되어 있다.
- 데이터 모델이 정의되어 있다.
- 에러 코드와 실패 응답 형식이 정의되어 있다.
- 외부 연동 timeout/retry/fallback 정책이 있다.

실패 시 조치:

- 병렬 개발을 멈추고 계약을 먼저 작성한다.

## 3. Gate 2: Implementation Gate

통과 조건:

- 계층 구조가 지켜졌다.
- 입력값 검증이 있다.
- 실패 처리가 있다.
- secret이 코드에 없다.
- 기본 테스트 또는 검증 방법이 있다.

실패 시 조치:

- merge하지 않는다.
- 누락된 검증과 실패 처리를 추가한다.

## 4. Gate 3: Integration Gate

통과 조건:

- 핵심 흐름이 처음부터 끝까지 동작한다.
- 외부 연동 실패 시 fallback이 동작한다.
- 잘못된 입력이 차단된다.
- 권한 없는 접근이 차단된다.

실패 시 조치:

- 기능을 feature flag로 끄거나 기본 흐름만 유지한다.
- 통합 실패 원인을 분리한다.

## 5. Gate 4: Security Gate

통과 조건:

- secret scan을 통과했다.
- 개인정보가 로그에 없다.
- 인증/인가가 확인되었다.
- 파일 업로드 또는 외부 입력 검증이 있다.
- 에러 응답에 내부 정보가 없다.

실패 시 조치:

- 보안 문제를 먼저 수정한다.
- 필요하면 키를 회전한다.
- 노출된 데이터가 있으면 영향 범위를 기록한다.

## 6. Gate 5: Release Gate

통과 조건:

- 테스트가 통과했다.
- 문서가 최신이다.
- known issue가 기록되었다.
- rollback 또는 fallback 계획이 있다.
- 운영 또는 발표 환경에서 핵심 시나리오가 검증되었다.

실패 시 조치:

- 릴리스하지 않는다.
- 범위를 줄이고 안정적인 기능만 배포한다.

## 7. Gate 6: Post-release Gate

통과 조건:

- 로그와 오류율을 확인했다.
- 사용자 피드백을 기록했다.
- 후속 작업이 정리되었다.
- 재발 방지 항목이 있다.

실패 시 조치:

- hotfix 또는 rollback을 검토한다.
- 다음 스프린트의 우선순위에 반영한다.
