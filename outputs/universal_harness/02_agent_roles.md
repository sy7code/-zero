# 02. Agent Roles

이 문서의 역할은 실제 팀원이 맡아도 되고, 한 사람이 여러 관점으로 리뷰할 때 사용해도 된다.

## 1. Product Planner

책임:

- 문제 정의, 사용자 흐름, MVP 범위를 고정한다.
- 기능 우선순위를 정한다.
- 범위 밖 항목을 명시한다.

검토 질문:

- 이 기능은 사용자 문제를 직접 해결하는가
- MVP에 꼭 필요한가
- 위험하거나 오해될 수 있는 기능인가
- 데모나 운영 시나리오로 설명 가능한가

## 2. System Architect

책임:

- 시스템 경계, 데이터 흐름, 모듈 책임을 정한다.
- 변경이 큰 구조 결정을 검토한다.
- 확장성과 교체 가능성을 확인한다.

검토 질문:

- 책임이 계층별로 분리되어 있는가
- 외부 서비스가 교체 가능하게 감싸져 있는가
- 데이터 흐름이 추적 가능한가
- 장애가 한 모듈에서 전체 장애로 번지지 않는가

## 3. Frontend Engineer

책임:

- 사용자 화면, 상태 관리, API 호출, 오류 상태를 구현한다.

검토 질문:

- 로딩, 성공, 실패 상태가 모두 있는가
- 사용자 입력 검증이 있는가
- 접근성 또는 사용성 문제가 없는가
- 클라이언트에 secret이 들어가지 않았는가

## 4. Backend Engineer

책임:

- API, 비즈니스 로직, DB 접근, 외부 연동을 구현한다.

검토 질문:

- router, service, repository, client 계층이 분리되어 있는가
- API 응답 형식이 일관적인가
- 입력값을 백엔드에서 검증하는가
- 외부 연동 실패 시 fallback이 있는가

## 5. Data Engineer

책임:

- 데이터 모델, 저장 정책, 마이그레이션, 조회 성능을 관리한다.

검토 질문:

- 테이블과 컬럼명이 일관적인가
- 개인정보 최소 수집 원칙을 지키는가
- 삭제 정책이 정해져 있는가
- 자주 조회되는 컬럼에 인덱스가 필요한가

## 6. AI/ML Engineer

책임:

- AI/ML 기능의 입력, 출력, 평가, 실패 대응을 설계한다.

검토 질문:

- 모델이 해야 하는 일과 하지 말아야 하는 일이 분리되어 있는가
- 모델 결과를 그대로 신뢰하지 않고 검증하는가
- fallback이 있는가
- 테스트 데이터와 평가 기준이 있는가
- 비용과 latency가 관리 가능한가

## 7. Security Reviewer

책임:

- 인증, 인가, secret, 개인정보, 파일 업로드, 외부 입력을 검토한다.

검토 질문:

- secret이 코드나 앱에 들어가지 않았는가
- 권한 없는 데이터 접근이 차단되는가
- 로그에 개인정보가 남지 않는가
- 파일 업로드 검증이 있는가
- 에러 응답에 내부 정보가 노출되지 않는가

## 8. QA/Release Engineer

책임:

- 정상 흐름, 실패 흐름, 릴리스 준비 상태를 검증한다.

검토 질문:

- 핵심 시나리오가 끝까지 동작하는가
- 실패 시나리오가 검증되었는가
- README만 보고 실행 가능한가
- 배포 또는 발표 환경에서 검증했는가

## 9. Maintainer

책임:

- 코드 구조, 문서화, 의존성, 장기 유지보수성을 관리한다.

검토 질문:

- 파일과 함수 책임이 명확한가
- 중복 로직이 과도하지 않은가
- 새 팀원이 구조를 이해할 수 있는가
- 임시 코드나 죽은 코드가 남아 있지 않은가

## 10. Requirements Challenger

책임:

- 사용자의 요구사항을 무조건 수용하지 않고, 목표, 위험, 범위, 검증 가능성 기준으로 비판적으로 검토한다.
- 요구사항이 모호하거나 과도하거나 위험하면 구현 전에 질문 또는 대안을 제시한다.
- 사용자 요청과 제품 목표가 충돌하면 충돌 지점을 명확히 적는다.

검토 질문:

- 이 요구사항은 실제 문제 해결에 필요한가
- MVP 범위를 불필요하게 키우는가
- 안전, 개인정보, 법률, 비용, 일정 위험을 높이는가
- 검증 가능한 acceptance criteria로 바꿀 수 있는가
- 더 작고 안전한 대안이 있는가

개입 기준:

- 요구사항이 must-have를 5개 초과하게 만들 때
- 법률, 의료, 금융, 안전 판단을 포함할 때
- 출처 없는 사실을 근거로 기능을 만들 때
- 구현 기간이나 팀 역량을 초과할 가능성이 높을 때
- 실패 시 사용자 피해가 큰 기능일 때

## 11. Independent QA Reviewer

책임:

- 만든 기능이 요구사항을 만족하는지만 보지 않고, 요구사항 자체가 올바른지와 실제 사용자 상황에서 실패하지 않는지를 검증한다.
- happy path보다 실패 경로, 악용 가능성, 사용성 문제, 오해 가능성을 우선 확인한다.

검토 질문:

- 이 기능은 요구사항대로 동작하지만 사용자에게는 여전히 불편하지 않은가
- 사용자가 잘못 입력하거나 모를 때도 진행 가능한가
- 기능이 위험한 확정 판단처럼 보이지 않는가
- 데모에서는 되지만 실제 사용 흐름에서는 깨지는 부분이 없는가
- 에러 상태와 fallback이 실제로 실행되었는가
