# 30. Failure Loop Harness

이 문서는 작업이 반복 실패하거나 같은 시도를 계속 반복하는 무한 루프를 막기 위한 하네스다. 목적은 실패를 숨기지 않고, 반복 횟수와 전환 기준을 정해 더 나은 접근으로 바꾸는 것이다.

## 1. Entry Criteria

다음 중 하나라도 해당하면 적용한다.

- 같은 명령, 테스트, 빌드, API 호출이 반복 실패한다.
- 같은 원인으로 2회 이상 수정이 실패한다.
- 오류 메시지가 바뀌지 않는다.
- 시도한 해결책이 효과가 없는데 계속 반복하고 있다.
- 외부 서비스, 권한, 네트워크, 환경 문제로 진행이 막힌다.

## 2. Failure Counter

반복 실패는 다음 기준으로 센다.

- 같은 명령이 같은 오류로 실패: 1회
- 같은 테스트가 같은 assertion/error로 실패: 1회
- 같은 API 호출이 같은 status/error로 실패: 1회
- 같은 파일 수정 후 같은 문제가 재발: 1회

기준:

- 2회 연속 실패: 원인 가설을 바꾼다.
- 3회 연속 실패: 같은 접근을 중단하고 대안을 선택한다.
- 4회 이상 실패: 사용자에게 현재 상태, 시도한 것, 필요한 정보를 보고한다.

## 3. Required Failure Log

2회 이상 실패하면 다음을 기록한다.

```text
작업 목표:
실패한 명령/행동:
오류 요약:
반복 횟수:
시도한 해결책:
현재 가설:
다음 대안:
필요한 정보 또는 권한:
```

## 4. Loop Break Rules

금지:

- 같은 명령을 오류 분석 없이 3회 이상 반복하지 않는다.
- 같은 patch를 근거 없이 반복하지 않는다.
- dependency 설치 실패를 무한 재시도하지 않는다.
- 네트워크/권한 문제가 명확한데 코드만 계속 고치지 않는다.
- 테스트 실패 원인을 읽지 않고 snapshot만 계속 갱신하지 않는다.

필수:

- 실패 출력에서 가장 구체적인 오류 1개를 찾는다.
- 환경 문제인지 코드 문제인지 분리한다.
- 최소 재현 단위를 만든다.
- 대안을 1개 이상 적는다.

## 5. Escalation Paths

실패 유형별 전환 기준:

### Build/Test Failure

1. 오류 로그를 읽는다.
2. 가장 작은 실패 테스트만 실행한다.
3. 최근 변경 diff와 연결한다.
4. 3회 실패하면 구현 접근을 바꾸거나 변경 범위를 줄인다.

### Dependency Failure

1. package manager와 lockfile 상태를 확인한다.
2. 버전 충돌인지 네트워크인지 확인한다.
3. 2회 실패하면 공식 문서 또는 lockfile 기준으로 접근을 바꾼다.
4. 3회 실패하면 dependency 추가 없이 가능한 대안을 검토한다.

### Permission or Sandbox Failure

1. 필요한 파일/네트워크 권한을 확인한다.
2. 권한 요청이 가능한지 확인한다.
3. 2회 실패하면 권한 없이 가능한 대안을 찾는다.
4. 권한이 필수면 사용자에게 필요한 권한과 이유를 묻는다.

### External API Failure

1. status code, response body, timeout을 확인한다.
2. API key, rate limit, request schema를 확인한다.
3. 2회 실패하면 mock 또는 fallback으로 진행한다.
4. 3회 실패하면 외부 연동을 optional로 내린다.

### Design or Requirement Failure

1. 요구사항이 모호한지 확인한다.
2. acceptance criteria를 다시 작성한다.
3. 2회 실패하면 요구사항을 더 작은 기능으로 쪼갠다.
4. 3회 실패하면 Requirements Challenger 관점으로 보류 또는 수정 제안한다.

## 6. User Communication Rule

다음 경우 사용자에게 보고한다.

- 같은 문제로 3회 연속 실패했다.
- 추가 권한, 계정, API key, 외부 상태가 필요하다.
- 요구사항이 현재 제약과 충돌한다.
- 대안 중 사용자 선택이 결과를 크게 바꾼다.

보고 형식:

```text
현재 막힌 지점:
시도한 것:
실패 원인 후보:
가능한 대안:
내 추천:
사용자에게 필요한 결정:
```

질문은 한 번에 3개 이하로 한다.

## 7. Recovery Decision Labels

Continue:

- 원인이 명확하고 다음 시도가 다르다.

Change Approach:

- 같은 접근이 2회 실패했고 다른 가설이 있다.

Fallback:

- 외부 연동, AI, CV, 배포 등 optional 기능이 실패했지만 핵심 흐름은 유지할 수 있다.

Ask User:

- 권한, 계정, API key, 요구사항 선택이 필요하다.

Stop:

- 현재 환경에서 더 진행하면 위험하거나 같은 실패를 반복한다.

## 8. Failure Loop Gate

다음 조건을 만족해야 같은 작업을 계속 진행한다.

- 반복 실패 횟수를 알고 있다.
- 이전 시도와 다른 접근이다.
- 실패 원인 가설이 바뀌었다.
- fallback 또는 사용자 보고 기준이 정해졌다.

실패 시 조치:

- 같은 접근을 중단한다.
- failure log를 작성한다.
- 대안으로 전환하거나 사용자에게 보고한다.
