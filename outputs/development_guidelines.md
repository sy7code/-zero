# 당황Zero 개발 기준 문서

이 문서는 당황Zero 프로젝트를 구현할 때 반드시 지켜야 할 개발 기준이다. 코드 작성, 리뷰, 수정, 기능 추가 시 이 문서를 기준으로 판단한다.

## 1. 프로젝트 기본 구조

최종 구조는 다음을 기본으로 한다.

```text
Flutter 앱 -> FastAPI 백엔드 -> Supabase DB/Storage
```

AI와 CV는 별도 서버를 필수로 두지 않고, 백엔드 내부 모듈 또는 백엔드가 호출하는 선택 기능으로 구현한다.

```text
FastAPI 백엔드
  ├─ 사고 기록 API
  ├─ 사진 업로드 API
  ├─ 체크리스트 추천 로직
  ├─ AI 분석/분류/정리 모듈
  └─ CV 사진 분석/검증 모듈
```

## 2. 역할 분리 기준

### 프론트엔드

- Flutter 앱 화면을 담당한다.
- 사진 촬영, 위치/시간 수집, 사고 유형 선택, 결과 표시를 담당한다.
- DB secret key, AI API key 등 민감한 키를 앱에 넣지 않는다.
- 앱은 백엔드 API만 호출한다.

### 백엔드

- FastAPI로 구현한다.
- 앱, DB, AI, CV를 연결하는 중심 계층이다.
- 사용자 입력 검증, 사고 기록 저장, 사진 저장, 결과 반환을 담당한다.
- DB 접근, 외부 API 호출, 비즈니스 로직을 한 파일에 섞지 않는다.

### AI

- 사고 상황 분석, 분류, 정리, 재질문 생성을 담당한다.
- 최종 안내 문구는 자유 생성하지 않고 체크리스트 DB에서 가져온다.
- 과실비율, 법적 책임, 보험금 판단은 하지 않는다.

### CV

- 사고 사진 항목 관리, 누락 확인, 이미지 품질 검사, 선택적 객체 탐지를 담당한다.
- CV 결과는 확정 판단이 아니라 보조 정보로 사용한다.
- 파손 여부, 부상 여부, 책임 여부를 단정하지 않는다.

## 3. 백엔드 아키텍처 기준

백엔드는 계층형 구조를 따른다.

```text
router -> service -> repository -> external client
```

- `router`: 요청과 응답 처리
- `service`: 비즈니스 로직 처리
- `repository`: DB 접근 처리
- `external client`: Supabase, AI API, CV 모델 등 외부 연동 처리

금지 사항:

- router에서 DB를 직접 호출하지 않는다.
- router에서 AI/CV를 직접 호출하지 않는다.
- repository에 체크리스트 추천 로직을 넣지 않는다.
- service에 Supabase 세부 구현을 과하게 노출하지 않는다.

## 4. SOLID 적용 기준

### SRP, 단일 책임 원칙

하나의 함수, 클래스, 파일은 하나의 책임만 가진다.

예:

- `PhotoService`: 사진 저장 및 검증
- `AccidentService`: 사고 기록 생성 및 조회
- `ChecklistService`: 체크리스트 추천
- `AiService`: 사고 상황 분석 및 요약
- `CvService`: 이미지 분석 및 사진 항목 검증

### OCP, 개방 폐쇄 원칙

기능 추가는 기존 코드를 크게 수정하지 않고 확장하는 방식으로 한다.

- 사고 유형은 코드에 하드코딩하지 않고 설정값, DB, JSON 등으로 분리한다.
- 체크리스트 항목은 코드가 아니라 데이터로 관리한다.
- 사고 유형이 추가되어도 기존 추천 로직 전체를 뜯어고치지 않게 한다.

### LSP, 리스코프 치환 원칙

같은 역할의 구현체는 교체 가능해야 한다.

예:

- `ManualPhotoAnalyzer`
- `OpenCvAnalyzer`
- `YoloAnalyzer`

위 구현체들은 같은 입력과 출력 형식을 유지해야 한다.

### ISP, 인터페이스 분리 원칙

하나의 큰 인터페이스에 모든 기능을 몰아넣지 않는다.

예:

- `AccidentClassifier`
- `AccidentSummarizer`
- `FollowupQuestionGenerator`
- `ChecklistMatcher`

### DIP, 의존성 역전 원칙

상위 로직이 특정 외부 서비스에 직접 의존하지 않게 한다.

- service는 Supabase SDK를 직접 알지 않도록 한다.
- AI API, CV 모델, Storage는 client 계층으로 감싼다.
- OpenAI, Gemini, 규칙 기반 로직을 교체할 수 있게 설계한다.

## 5. 보안 기준

### Secret 관리

- API key, DB URL, service role key, JWT secret은 코드에 직접 작성하지 않는다.
- 민감한 값은 `.env`에 저장한다.
- `.env`는 Git에 올리지 않는다.
- `.gitignore`에 `.env`를 반드시 포함한다.
- Flutter 앱에는 secret key를 넣지 않는다.

### 개인정보 보호

보호 대상:

- 차량번호
- 전화번호
- 사고 위치
- 사고 사진
- 보험사 정보
- 사고 기록

규칙:

- 필요한 정보만 저장한다.
- 테스트와 발표에는 실제 차량번호, 전화번호, 실제 사고 사진을 사용하지 않는다.
- 파일명에 차량번호, 전화번호 등 개인정보를 넣지 않는다.
- 개인정보를 로그에 남기지 않는다.
- 사고 기록 ID는 순차 번호 대신 UUID를 사용한다.
- 사고 기록 조회는 본인 데이터만 가능하도록 설계한다.

### 입력값 검증

프론트 검증만 믿지 않고 백엔드에서 다시 검증한다.

검증 대상:

- 사고 유형
- 차량번호
- 전화번호
- 위도, 경도
- 사진 파일 확장자
- 사진 파일 MIME type
- 사진 파일 크기
- 체크리스트 항목 ID

예:

- 위도는 `-90`에서 `90` 사이여야 한다.
- 경도는 `-180`에서 `180` 사이여야 한다.
- 이미지는 `jpg`, `jpeg`, `png`만 허용한다.
- 파일 크기 제한을 둔다.

### 파일 업로드 보안

- 원본 파일명을 그대로 저장하지 않는다.
- UUID 기반 파일명으로 저장한다.
- 이미지 확장자와 MIME type을 검사한다.
- 실행 파일 업로드를 차단한다.
- 업로드 파일 크기를 제한한다.
- 사진은 DB에 직접 저장하지 않고 Storage에 저장한다.
- DB에는 storage path 또는 URL만 저장한다.

### 에러 응답 보안

- 사용자에게 내부 에러, DB 에러, stack trace를 노출하지 않는다.
- API key나 서버 경로가 응답에 포함되지 않게 한다.

좋은 예:

```json
{
  "success": false,
  "message": "사고 기록 저장에 실패했습니다"
}
```

나쁜 예:

```json
{
  "error": "Supabase key xxx failed at table accidents"
}
```

## 6. API 설계 기준

REST API 규칙을 따른다.

예:

```text
POST /accidents
GET /accidents/{accident_id}
POST /accidents/{accident_id}/photos
GET /accidents/{accident_id}/checklist
```

규칙:

- URL은 명사 중심으로 작성한다.
- HTTP method 의미를 지킨다.
- 성공/실패 응답 형식을 통일한다.
- HTTP 상태 코드를 적절히 사용한다.

응답 형식:

```json
{
  "success": true,
  "data": {},
  "message": "ok"
}
```

실패 형식:

```json
{
  "success": false,
  "message": "요청 처리에 실패했습니다",
  "code": "ACCIDENT_CREATE_FAILED"
}
```

## 7. DB 설계 기준

- Supabase PostgreSQL을 기본 DB로 사용한다.
- 사진 파일은 Supabase Storage에 저장한다.
- DB에는 사진 path 또는 URL만 저장한다.
- 주요 테이블에는 `id`, `created_at`, `updated_at`을 둔다.
- 테이블명과 컬럼명은 일관되게 작성한다.
- 사고 기록, 차량 정보, 사진 정보, 체크리스트 결과를 분리한다.
- 삭제 정책을 정한다. 기본은 soft delete를 고려한다.
- 자주 조회하는 컬럼에는 인덱스를 고려한다.

예상 테이블:

- `users`
- `vehicles`
- `accidents`
- `accident_photos`
- `checklist_results`
- `checklist_items`
- `accident_type_rules`

## 8. AI 안전 기준

AI가 할 수 있는 일:

- 사고 상황 분석
- 사고 유형 후보 분류
- 긴급도 후보 분류
- 사고 내용 요약
- 누락 정보 확인
- 채팅형 재질문 생성
- 체크리스트 추천 보조

AI가 하면 안 되는 일:

- 과실비율 판단
- 법적 책임 판단
- 보험금 판단
- 신고 필요 여부 단정
- 사고 원인 단정
- 파손 확정 판단

규칙:

- 최종 안내 문구는 AI가 자유 생성하지 않는다.
- 안내 문구는 검증된 체크리스트 DB에서 가져온다.
- AI 결과는 참고용으로 표시한다.
- 긴급 상황은 AI 판단보다 112/119 안내를 우선한다.
- AI 응답은 그대로 사용자에게 전달하지 않고 검증 과정을 거친다.

## 9. CV 안전 기준

CV가 할 수 있는 일:

- 차량 감지
- 사람 감지
- 신호등/표지판 감지
- 사진 품질 검사
- 사진 항목 누락 가능성 표시
- 파손 의심 영역 후보 표시

CV가 하면 안 되는 일:

- 파손 여부 확정
- 사고 책임 판단
- 사람 부상 여부 단정
- 번호판 인식 결과를 확정값으로 저장

규칙:

- CV 결과는 보조 정보로만 사용한다.
- confidence 기준을 정한다.
- confidence가 낮은 결과는 사용자 확인 대상으로 처리한다.
- CV 실패 시에도 기본 체크리스트 기능은 동작해야 한다.

## 10. 에러 처리와 Fallback 기준

- 위치 권한 거부 시 수동 입력을 제공한다.
- 사진 업로드 실패 시 재시도할 수 있게 한다.
- AI/CV 분석 실패 시 기본 체크리스트를 제공한다.
- 서버 오류 시 사용자가 이해할 수 있는 메시지를 제공한다.
- 내부 로그와 사용자 메시지를 분리한다.
- 특정 기능이 실패해도 전체 사고 기록 흐름이 멈추지 않게 한다.

## 12. Git 및 협업 기준

- `main` 브랜치에 직접 push하지 않는다.
- 기능 단위 브랜치를 사용한다.
- 커밋 메시지는 Conventional Commits를 따른다.

예:

```text
feat: 사고 기록 생성 API 추가
fix: 사진 업로드 오류 처리
docs: README 실행 방법 추가
refactor: 체크리스트 추천 로직 분리
test: 사고 기록 생성 테스트 추가
```

규칙:

- 기능 개발 전 issue 또는 task를 만든다.
- merge 전 최소 1명 이상 코드 리뷰한다.
- 충돌 해결 시 다른 사람 코드를 임의로 삭제하지 않는다.
- 작업 단위는 리뷰 가능한 크기로 유지한다.

## 13. 코드 리뷰 기준

리뷰할 때 반드시 확인한다.

- 함수가 한 가지 책임만 갖는가
- secret key가 코드에 들어가지 않았는가
- 사용자 입력 검증이 있는가
- 개인정보가 로그에 남지 않는가
- AI/CV가 확정 판단을 하지 않는가
- router, service, repository 계층이 지켜졌는가
- 실패 상황에 대한 fallback이 있는가
- 코드 이름만 보고 역할을 이해할 수 있는가
- 중복 로직이 과도하지 않은가
- 테스트 또는 수동 검증이 되었는가

## 15. 최종 개발 원칙

당황Zero는 사고 판단 앱이 아니라 사고 직후 초기 대응을 돕는 보조 앱이다.

따라서 개발 시 다음 원칙을 지킨다.

- AI/CV는 판단자가 아니라 보조자로 제한한다.
- 개인정보와 secret key를 절대 노출하지 않는다.
- 기능은 작게 나누고 계층을 분리한다.
- 기존 코드를 크게 뜯지 않고 확장 가능하게 설계한다.
- 실패 상황에서도 기본 체크리스트 흐름은 유지한다.
- 발표와 테스트에는 실제 개인정보를 사용하지 않는다.
