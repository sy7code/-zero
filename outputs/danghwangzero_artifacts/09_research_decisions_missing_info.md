# 당황Zero Research, Decisions, and Missing Information

이 문서는 당황Zero 구현 전 결정의 근거, 출처 필요 항목, 가정, 부족한 정보를 정리한다. 출처가 없는 내용은 사실이 아니라 가정으로 취급한다.

## 0. Current Priority

현재 바로 확정할 항목은 `팀원별 실제 역할 배정`이다.

이번 단계에서 보류하는 항목:

- 공식 출처 수집: 체크리스트 문구를 최종 확정하기 전 조사 단계에서 수행한다.
- threat model: 실제 API, DB, 사진 저장 방식이 정해진 뒤 보안 점검 단계에서 수행한다.
- 기술 공식 문서 확인: FastAPI, Supabase, Flutter, OpenCV, YOLO를 실제 사용하기로 확정한 뒤 ADR 또는 조사 기록에 출처를 붙인다.

즉, 지금은 팀원별 owner map을 먼저 확정하고, 출처/위험 분석은 구현 전 Gate에서 빠지지 않도록 추적만 한다.

## 1. Source Policy

자료조사와 의사결정은 다음 출처 우선순위를 따른다.

1. 경찰청, 소방청, 도로교통공단, 공공데이터포털, 보험사 공식 사고 안내
2. Flutter, FastAPI, Supabase, OpenCV, Ultralytics 공식 문서
3. 신뢰 가능한 기술 블로그 또는 기업 엔지니어링 블로그
4. 일반 블로그, 커뮤니티 글, 영상 자료

안전, 신고, 개인정보, 사고 대응 문구는 1순위 출처를 우선한다.

## 2. Decisions

## D-01. 앱은 사고 판단이 아니라 초기 대응 보조에 집중한다

선택지:

- 사고 판단 앱
- 초기 대응 기록/안내 앱

근거:

- 사고 직후 사용자는 판단보다 기록과 행동 순서 안내가 필요하다.
- 법적 책임, 과실비율, 보험금 판단은 위험도가 높고 공식 기관/보험사 판단 영역이다.

출처:

- 필요: 경찰청/도로교통공단/보험사 공식 사고 대응 안내
- 현재 상태: 발표 자료 기반 가정

가정:

- 프로젝트 범위상 공식 판단 기능은 구현하지 않는다.

신뢰도:

- Medium, 공식 출처 보강 필요

재검토 조건:

- 교수/평가 기준에서 공식 자료 기반 사고 대응 근거를 요구하는 경우

## D-02. 사고 유형 직접 선택보다 단계형 질문 기반 유추를 사용한다

선택지:

- 사용자가 사고 유형을 직접 선택
- 앱이 질문을 통해 상황 후보 유추

근거:

- 사고 직후 사용자는 본인이 어떤 사고 유형인지 판단하기 어렵다.
- 버튼/칩/카드형 질문은 채팅보다 빠르고 조작이 쉽다.

출처:

- 필요: 사용성 근거 또는 자체 사용자 테스트
- 현재 상태: 제품 UX 가정

가정:

- 평가자는 채팅보다 단계형 UI를 더 쉽게 이해한다.

신뢰도:

- Medium

재검토 조건:

- 사용자 테스트에서 질문 흐름이 더 어렵다는 피드백이 나오는 경우

## D-03. 백엔드는 FastAPI를 사용한다

선택지:

- FastAPI
- Spring Boot
- Firebase Functions

근거:

- AI/CV와 Python 생태계 연동이 쉽다.
- Swagger 문서 자동화가 가능하다.
- MVP 구현 속도가 빠르다.

출처:

- 필요: FastAPI 공식 문서
- 현재 상태: 기술 선택 가정

가정:

- 팀이 Python 백엔드 구현을 감당할 수 있다.

신뢰도:

- Medium, 팀 역량 확인 필요

재검토 조건:

- 팀 백엔드 담당자가 Spring Boot 경험이 압도적으로 많고 AI/CV를 별도 Python 모듈로 분리하기로 결정한 경우

## D-04. DB/Storage는 Supabase를 사용한다

선택지:

- Supabase
- Firebase
- 직접 PostgreSQL 서버

근거:

- 사고 기록은 관계형 데이터로 정리하기 좋다.
- Storage로 사진 저장을 함께 처리할 수 있다.
- 무료 범위 MVP에 적합하다.

출처:

- 필요: Supabase 공식 문서/가격 정책
- 현재 상태: 기술 선택 가정

가정:

- 무료 플랜 한도 안에서 데모 데이터와 사진 저장이 가능하다.

신뢰도:

- Medium, 무료 한도 확인 필요

재검토 조건:

- Supabase 무료 한도 또는 학교 네트워크 환경이 시연에 맞지 않는 경우

## D-05. AI/CV는 기본 흐름의 필수 의존성이 아니다

선택지:

- AI/CV 필수
- AI/CV 선택적 고도화

근거:

- 모델 성능이 낮아도 앱의 핵심 흐름이 동작해야 한다.
- 평가 안정성을 위해 규칙 기반 fallback이 필요하다.

출처:

- 필요: 자체 테스트 결과
- 현재 상태: 구현 안정성 판단

가정:

- 규칙 기반 상황 후보와 체크리스트만으로 MVP 가치가 충분하다.

신뢰도:

- High

재검토 조건:

- 평가 기준에서 AI/CV 모델 시연 비중이 매우 높은 경우

## D-06. PhotoFacts와 NextAction 계약을 추가한다

선택지:

- CV/AI 결과를 화면과 규칙에서 직접 사용
- `PhotoFacts`와 `NextAction` 중간 계약으로 분리

근거:

- 비전 API, Gemini, YOLO, mock이 바뀌어도 분류/누락 분석/화면 흐름을 유지할 수 있다.
- mock PhotoFacts만으로 AI/CV 없이 핵심 흐름을 먼저 구현하고 검증할 수 있다.
- `because` 근거를 남기면 발표 때 내부 동작을 설명하기 쉽다.

출처:

- 참고 자료: `당황Zero_설계제안.html`
- 현재 상태: 설계 제안 기반 채택

가정:

- 팀이 JSON 계약을 먼저 맞추면 프론트, 백엔드, AI, CV가 병렬 작업할 수 있다.

신뢰도:

- High

재검토 조건:

- 팀원이 계약 기반 구현보다 단순 CRUD 구현을 우선해야 할 정도로 일정이 짧은 경우

## D-07. Google Vision/Gemini/YOLO는 확정 기술이 아니라 후보 실험으로 둔다

선택지:

- Cloud Vision 또는 Gemini를 바로 MVP 필수 기능으로 확정
- 수동 사진 항목 체크와 mock PhotoFacts를 MVP로 두고, 비전 기술은 30장 시험 후 결정

근거:

- 현재 프로젝트의 핵심 가치는 사고 직후 흐름 안내와 누락 방지다.
- 비전 인식률이 낮아도 앱은 끝까지 동작해야 한다.
- 참고 자료에서도 Cloud Vision이 차량, 번호판, 파손, 스키드마크를 실제로 얼마나 잘 채우는지는 직접 시험이 필요하다고 정리되어 있다.

출처:

- 참고 자료: `당황Zero_설계제안.html`
- 필요: Google Cloud Vision, Gemini, Ultralytics, OpenCV 공식 문서와 30장 자체 시험 결과

가정:

- 무료 또는 저비용 범위에서 30장 실험은 가능하다. 단, 최신 가격/무료 한도는 공식 문서로 재확인해야 한다.

신뢰도:

- Medium, 공식 문서와 자체 실험 필요

재검토 조건:

- 평가자가 실제 비전 모델 사용을 필수로 요구하는 경우
- 30장 시험에서 특정 기술의 채움률이 충분히 높은 경우

## D-08. React/웹 전제와 Cloudflare 터널 전제는 제외한다

선택지:

- 참고 자료의 웹/React 디버그 전제를 그대로 사용
- 모바일 앱 구조에 맞게 Flutter 앱, FastAPI, 개발용 로그/디버그 API 중심으로 수정

근거:

- 사용자가 명시한 프로젝트 형태는 앱이다.
- Flutter 앱에서는 React 화면 전제를 그대로 가져오면 구현 방향이 어긋난다.
- 터널/HTTPS/브라우저 제약은 웹 시연일 때 중요하지만, Android 앱/APK 또는 로컬 API 시연 방식이 정해진 뒤 다시 판단하는 편이 낫다.

출처:

- 사용자 요구: 앱 프로젝트
- 참고 자료: `당황Zero_설계제안.html`

가정:

- 시연은 Android 폰 또는 에뮬레이터 기반으로 진행한다.

신뢰도:

- High

재검토 조건:

- 최종 시연을 웹앱으로 전환하는 경우

## 3. Missing Information

## High Impact

아래 정보는 답에 따라 MVP 범위나 기술 선택이 바뀔 수 있다.

1. 팀원별 실제 기술 숙련도
   - Flutter 경험
   - Python/FastAPI 경험
   - Supabase 경험
   - OpenCV/YOLO 경험

2. 평가 방식
   - 라이브 데모인지 영상 제출인지
   - 평가자가 앱을 직접 조작하는지
   - AI/CV 기능을 반드시 보여줘야 하는지

3. 개발 기간
   - 실제 남은 주차
   - 중간 점검일
   - 최종 발표일

4. 실행 환경
   - Android 기기 사용 가능 여부
   - 학교 네트워크에서 외부 API/Supabase 접근 가능 여부
   - 백엔드 서버를 어디에서 실행할지

5. 공식 자료 요구 수준
   - 사고 대응 체크리스트에 출처를 반드시 표시해야 하는지
   - 발표자료에 출처 슬라이드가 필요한지

6. 비전 실험 가능 범위
   - 팀이 직접 촬영 가능한 사진 수
   - 실제 번호판을 마스킹할 방법
   - Cloud Vision/Gemini 테스트에 사용할 계정과 비용 한도

## Medium Impact

1. 로그인 구현 여부
2. 사고 기록을 여러 건 저장해야 하는지
3. 사진을 실제로 업로드할지, 데모에서는 더미 이미지로 대체할지
4. LLM API 비용 사용 가능 여부
5. YOLO 데모가 필수인지 선택인지

## Low Impact

1. 앱 색상/브랜드 스타일
2. 아이콘 세트
3. 체크리스트 문구 세부 표현
4. 요약 화면 레이아웃

## 4. Questions for Team Meeting

한 번에 결정해야 할 질문은 5개다. 단, 현재 회의에서 시간이 부족하면 2번을 먼저 결정한다.

1. 최종 발표에서 라이브 데모를 할 것인가, 영상 데모를 할 것인가?
2. 팀원 4명의 실제 가능 기술은 무엇인가?
3. AI/CV는 필수 시연인가, 고도화 시연인가?
4. 백엔드는 로컬 실행인가, 외부 배포인가?
5. 사고 대응 체크리스트에 공식 출처를 슬라이드나 앱에 표시해야 하는가?
