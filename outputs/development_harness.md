# 당황Zero 개발 하네스

이 문서는 당황Zero 프로젝트를 구현할 때 사용할 개발 하네스다. 하네스란 기능을 그냥 만들기만 하는 것이 아니라, 역할 분리, 작업 순서, 자동/수동 검증, 수정 루프, 리뷰 기준까지 포함한 개발 운영 구조를 뜻한다.

코드 작성 시 `development_guidelines.md`와 함께 이 문서를 기준으로 따른다.

## 1. 하네스 목표

당황Zero 개발 하네스의 목표는 다음과 같다.

- 기능을 작게 나누고 안전하게 통합한다.
- 프론트, 백엔드, AI, CV 작업을 병렬로 진행하되 API 계약을 먼저 고정한다.
- AI/CV 실패 시에도 앱의 핵심 흐름이 유지되게 한다.
- 코드 작성 후 반드시 검증과 수정 루프를 거친다.
- 보안, 개인정보, 유지보수 기준을 기능 개발 중간에 계속 확인한다.

## 2. 서브 에이전트 역할

프로젝트를 진행할 때 다음 역할을 둔다. 실제 사람이 맡아도 되고, 코드 작성 시 관점별 리뷰 기준으로 사용해도 된다.

### 2.1 Product Planner

역할:

- 사용자 흐름과 MVP 범위를 고정한다.
- 기능이 사고 판단이 아니라 초기 대응 보조 목적에 맞는지 확인한다.
- 기능 우선순위를 정한다.

확인 항목:

- 접촉사고와 시설물 파손 중심 MVP 범위를 벗어나지 않았는가
- 과실비율, 법적 책임, 보험금 판단 기능이 들어가지 않았는가
- 데모 시나리오가 끝까지 설명 가능한가

산출물:

- 기능 목록
- 사용자 흐름
- 데모 시나리오

### 2.2 Frontend Engineer

역할:

- Flutter 앱 화면과 상태 흐름을 구현한다.
- 카메라, 사진 업로드, 위치/시간 수집, 결과 표시를 담당한다.
- API 응답 실패 시 사용자에게 안전한 fallback UI를 제공한다.

확인 항목:

- 앱에 secret key가 들어가지 않았는가
- 위치 권한 거부 시 수동 입력이 가능한가
- 사진 업로드 실패 시 재시도가 가능한가
- 로딩, 성공, 실패 상태가 화면에 반영되는가

산출물:

- Flutter 화면
- API 연동 코드
- 수동 테스트 시나리오 결과

### 2.3 Backend Engineer

역할:

- FastAPI 서버, API 계약, DB 연동, Storage 연동을 담당한다.
- router, service, repository, external client 계층을 유지한다.
- 프론트, AI, CV 사이의 데이터 흐름을 조율한다.

확인 항목:

- API 요청/응답 스키마가 문서화되었는가
- 입력값 검증이 백엔드에서 수행되는가
- 개인정보와 secret이 로그나 응답에 노출되지 않는가
- AI/CV 실패 시 기본 체크리스트가 반환되는가

산출물:

- FastAPI API
- Supabase schema
- Swagger 문서
- API 테스트 결과

### 2.4 AI Engineer

역할:

- 사고 상황 분석, 분류, 정리, 재질문 로직을 설계한다.
- 체크리스트 DB와 규칙 기반 케이스 매칭을 담당한다.
- 필요 시 LLM API를 요약/재질문 보조에만 사용한다.

확인 항목:

- AI가 최종 안내 문구를 자유 생성하지 않는가
- 과실비율, 법적 책임, 보험금 판단을 하지 않는가
- 긴급 상황에서 112/119 안내가 우선되는가
- 규칙이 데이터 또는 설정으로 분리되어 있는가

산출물:

- 사고 유형 규칙
- 체크리스트 매칭 로직
- 요약/재질문 로직
- AI 안전 테스트 케이스

### 2.5 CV Engineer

역할:

- 사진 항목 관리, 누락 확인, 이미지 품질 검사, 선택적 객체 탐지를 담당한다.
- MVP에서는 수동 사진 항목 체크를 우선한다.
- 고도화 시 OpenCV 또는 YOLO를 붙인다.

확인 항목:

- CV 결과가 확정 판단으로 표현되지 않는가
- 모델 실패 시 수동 체크 방식으로 fallback되는가
- confidence 기준이 있는가
- 파손, 부상, 책임을 단정하지 않는가

산출물:

- 사진 항목 검증 로직
- OpenCV 품질 검사, 선택
- YOLO 탐지 데모, 선택
- CV 실패 fallback 테스트

### 2.6 Security Reviewer

역할:

- 개인정보, 인증/인가, secret, 파일 업로드 보안을 검토한다.

확인 항목:

- `.env`가 Git에 올라가지 않는가
- Supabase service role key가 앱에 들어가지 않는가
- 사고 기록 조회가 본인 데이터로 제한되는가
- 파일 확장자, MIME type, 크기 검증이 있는가
- 로그에 차량번호, 전화번호, 위치, 사진 URL이 과도하게 남지 않는가

산출물:

- 보안 리뷰 체크리스트
- 수정 요청 목록

### 2.7 QA/Release Engineer

역할:

- 기능 완성 여부를 사용자 흐름 기준으로 검증한다.
- 배포 전 데모 시나리오와 실패 시나리오를 반복 테스트한다.

확인 항목:

- 핵심 흐름이 끝까지 동작하는가
- 실패 경로에서 앱이 멈추지 않는가
- 발표 데모 데이터가 준비되었는가
- README와 실행 방법이 최신인가

산출물:

- 테스트 결과
- 버그 목록
- 릴리스 체크리스트

## 3. 개발 파이프라인

모든 기능은 다음 순서로 진행한다.

```text
요구사항 확정
  -> API/데이터 계약 작성
  -> 작은 단위 구현
  -> 로컬 검증
  -> 통합 검증
  -> 보안/품질 리뷰
  -> 수정
  -> 데모 시나리오 검증
  -> merge
```

## 4. 단계별 작업 흐름

### 4.1 Discovery

목표:

- 모르는 것을 먼저 확인한다.
- 기능 범위와 위험 요소를 고정한다.

작업:

- MVP 사고 유형을 확정한다.
- 앱 화면 흐름을 확정한다.
- API 목록을 초안으로 만든다.
- DB 테이블을 초안으로 만든다.
- AI/CV를 필수 기능과 고도화 기능으로 나눈다.

통과 조건:

- MVP 범위가 접촉사고, 시설물 파손 중심으로 정리되어 있다.
- 과실비율, 법적 책임, 보험금 판단이 범위 밖으로 명시되어 있다.
- 핵심 사용자 흐름이 한 줄로 설명된다.

실패 시 조치:

- 기능 범위를 줄인다.
- AI/CV 의존 기능을 고도화 단계로 내린다.

### 4.2 Foundation

목표:

- 병렬 개발 전에 계약과 골격을 만든다.

작업:

- Flutter 프로젝트 생성
- FastAPI 프로젝트 생성
- Supabase 프로젝트 생성
- `.env.example` 작성
- API 응답 형식 고정
- DB schema 초안 작성
- checklist seed data 작성

통과 조건:

- 앱이 백엔드 health check를 호출할 수 있다.
- 백엔드가 Supabase에 연결된다.
- Swagger에서 기본 API를 확인할 수 있다.
- secret은 `.env`로 분리되어 있다.

실패 시 조치:

- 기능 구현을 멈추고 환경과 계약부터 고친다.

### 4.3 Vertical Slice

목표:

- 최소 동작 경로를 끝까지 연결한다.

최소 경로:

```text
앱에서 사고 시작
  -> 사고 유형 선택
  -> 위치/시간 저장
  -> 사진 업로드
  -> 체크리스트 추천
  -> 결과 화면 표시
```

작업:

- `POST /accidents`
- `POST /accidents/{id}/photos`
- `GET /accidents/{id}/checklist`
- 기본 체크리스트 추천 로직
- 결과 화면

통과 조건:

- AI/CV 없이도 사고 기록 생성부터 결과 표시까지 동작한다.
- 사진 업로드 실패 시 재시도 가능하다.
- 위치 권한 거부 시 수동 입력으로 진행 가능하다.

실패 시 조치:

- AI/CV 작업을 중단하고 기본 흐름을 먼저 복구한다.

### 4.4 Expansion

목표:

- AI, CV, 예외 처리를 넓힌다.

작업:

- 사고 유형별 규칙 추가
- 누락 정보 재질문 추가
- 사고 요약 추가
- 사진 항목 누락 체크 추가
- OpenCV 품질 검사 추가, 선택
- YOLO 탐지 추가, 선택

통과 조건:

- AI가 분석, 분류, 정리, 재질문 역할만 수행한다.
- 체크리스트 안내는 DB에서 가져온다.
- CV 실패 시 수동 사진 항목 체크로 대체된다.

실패 시 조치:

- AI/CV 기능을 feature flag로 끄고 기본 흐름으로 되돌린다.

### 4.5 Hardening

목표:

- 보안, 안정성, 유지보수성을 강화한다.

작업:

- 입력값 검증 강화
- 파일 업로드 검증
- 인증/인가 확인
- 개인정보 로그 제거
- 단위 테스트 추가
- API 테스트 추가
- README 정리

통과 조건:

- 잘못된 입력값이 백엔드에서 차단된다.
- 잘못된 파일 업로드가 차단된다.
- 사고 기록 조회 권한이 검증된다.
- 에러 응답에 내부 정보가 노출되지 않는다.

실패 시 조치:

- 릴리스하지 않고 보안/권한 문제를 먼저 수정한다.

### 4.6 Release

목표:

- 발표와 시연 가능한 상태로 고정한다.

작업:

- 데모 데이터 생성
- 데모 시나리오 반복 테스트
- 발표용 제한사항 정리
- 실행 방법 문서화
- 마지막 회귀 테스트

통과 조건:

- 정해진 데모 시나리오가 3회 이상 연속 성공한다.
- README만 보고 실행할 수 있다.
- 발표용 데이터에 실제 개인정보가 없다.

실패 시 조치:

- 데모 범위를 줄이고 안정적인 흐름만 발표한다.

## 5. 검증 게이트

### 5.1 설계 게이트

통과 조건:

- 기능 범위가 명확하다.
- API 계약 초안이 있다.
- DB 테이블 초안이 있다.
- AI/CV가 필수 기능과 선택 기능으로 나뉘어 있다.

자동 검증:

- 없음

수동 검증:

- 팀 리뷰
- 발표 시나리오 검토

### 5.2 구현 시작 게이트

통과 조건:

- 프로젝트 실행 방법이 정리되어 있다.
- `.env.example`이 있다.
- secret이 코드에 없다.
- health check API가 동작한다.

자동 검증:

- lint
- backend import check
- health check

수동 검증:

- Swagger 접속
- Flutter 앱 실행

### 5.3 최소 기능 게이트

통과 조건:

- 사고 기록 생성이 가능하다.
- 사진 업로드가 가능하다.
- 체크리스트 결과가 앱에 표시된다.
- AI/CV 없이도 흐름이 완성된다.

자동 검증:

- API 테스트
- 단위 테스트

수동 검증:

- 실제 앱에서 데모 흐름 실행

### 5.4 통합 게이트

통과 조건:

- 앱, 백엔드, DB, Storage가 연결된다.
- AI/CV 모듈 실패 시 fallback이 동작한다.
- 잘못된 입력과 파일 업로드가 차단된다.

자동 검증:

- API integration test
- file validation test
- checklist fallback test

수동 검증:

- 위치 권한 거부
- 사진 업로드 실패
- 네트워크 오류

### 5.5 보안 게이트

통과 조건:

- secret이 repository에 없다.
- 개인정보가 로그에 남지 않는다.
- 본인 사고 기록만 조회 가능하다.
- 에러 응답에 내부 정보가 없다.

자동 검증:

- secret scan
- test for unauthorized access

수동 검증:

- 로그 샘플 확인
- API 응답 확인

### 5.6 릴리스 게이트

통과 조건:

- 데모 시나리오가 안정적으로 동작한다.
- README가 최신이다.
- 실제 개인정보가 없다.
- known issue가 정리되어 있다.

자동 검증:

- backend tests
- frontend build

수동 검증:

- 발표 환경에서 앱 실행
- 데모 계정과 데모 데이터 확인

## 6. 수정 루프

기능 개발 중 문제가 발견되면 다음 루프를 따른다.

```text
문제 발견
  -> 재현 조건 기록
  -> 원인 범위 분리
  -> 최소 수정
  -> 관련 테스트 추가 또는 갱신
  -> 회귀 테스트
  -> 리뷰
```

규칙:

- 재현 조건 없이 추측으로 수정하지 않는다.
- 수정 범위를 문제와 관련된 곳으로 제한한다.
- 보안 문제는 기능보다 우선 처리한다.
- AI/CV 문제는 기본 체크리스트 흐름을 깨지 않는 방식으로 수정한다.
- 수정 후 같은 문제가 다시 생기지 않도록 테스트나 체크리스트를 추가한다.

## 7. 자동 검증 추천 구성

가능하면 GitHub Actions 또는 로컬 스크립트로 다음을 자동화한다.

백엔드:

- Python formatting check
- lint
- type/import check
- pytest
- FastAPI health check

프론트:

- Flutter analyze
- Flutter test
- Flutter build, 가능하면

보안:

- `.env` commit 여부 확인
- secret 문자열 패턴 검사
- dependency 취약점 확인, 가능하면

API:

- Swagger 확인
- Postman collection 또는 간단한 integration test

## 8. 수동 검증 시나리오

### 정상 시나리오

```text
앱 실행
  -> 사고 대응 시작
  -> 접촉사고 선택
  -> 위치/시간 자동 저장
  -> 사진 촬영/업로드
  -> 누락 항목 확인
  -> 체크리스트 추천
  -> 사고 요약 확인
```

### 실패 시나리오

- 위치 권한 거부
- 사진 업로드 실패
- 네트워크 끊김
- AI 분석 실패
- CV 분석 실패
- 잘못된 파일 업로드
- 권한 없는 사고 기록 조회

각 실패 시나리오는 앱이 멈추지 않고 안전한 안내를 제공해야 한다.

## 9. Feature Flag 기준

AI/CV 기능은 안정성이 낮을 수 있으므로 feature flag로 켜고 끌 수 있게 설계한다.

예:

```text
ENABLE_AI_SUMMARY=true
ENABLE_CV_ANALYSIS=false
ENABLE_YOLO_DETECTION=false
```

규칙:

- AI/CV를 꺼도 기본 사고 기록과 체크리스트 추천은 동작해야 한다.
- 발표 전 불안정한 기능은 끄고 안정적인 흐름을 우선한다.
- 고도화 기능은 기본 기능을 깨지 않는 범위에서만 활성화한다.

## 10. 완료 정의

기능은 코드가 작성되었다고 완료가 아니다. 아래 조건을 만족해야 완료다.

- 요구사항과 범위에 맞게 구현되었다.
- API 계약이 문서와 일치한다.
- 정상 흐름이 테스트되었다.
- 실패 흐름이 테스트되었다.
- 개인정보와 secret이 노출되지 않는다.
- AI/CV가 확정 판단을 하지 않는다.
- fallback이 있다.
- README 또는 관련 문서가 갱신되었다.
- 최소 1명 이상 리뷰했다.

## 11. 코드 작성 시 적용 원칙

앞으로 코드를 작성할 때는 다음 순서를 따른다.

1. 기능 목적과 범위를 확인한다.
2. API/DB/화면 계약을 먼저 확인하거나 작성한다.
3. 계층 구조에 맞게 파일을 나눈다.
4. 작은 단위로 구현한다.
5. 입력 검증과 실패 처리를 같이 작성한다.
6. 테스트 또는 검증 방법을 추가한다.
7. 보안/개인정보 기준을 확인한다.
8. 기존 기능 회귀가 없는지 확인한다.

## 12. 최종 운영 원칙

당황Zero의 개발은 다음 원칙을 따른다.

- 기본 흐름이 먼저이고 AI/CV는 그 다음이다.
- 계약 없는 병렬 개발을 하지 않는다.
- 검증 없는 merge를 하지 않는다.
- 보안 문제는 기능 완성보다 우선한다.
- 실패 시나리오를 정상 시나리오만큼 중요하게 본다.
- 발표 직전에는 새로운 기능보다 안정성을 우선한다.
